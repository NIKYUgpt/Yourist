# Как оценивать поиск в диалоге

Дата: 05.11.2026. Статус: протокол будущего эксперимента, **не результат замера**.

## Исследовательский вопрос

Помогает ли преобразование уточнения в самостоятельный запрос находить нужные
нормы по сравнению с поиском только по последней реплике и простым добавлением
предыдущих вопросов? Отдельный риск — перенос устаревших обстоятельств или ошибки
из предыдущего ответа в новую реплику.

## Что уже проверено

Автотесты `tests/assistant/test_dialogs.py`, `test_context.py` и
`tests/deid/test_sessions.py` проверяют инженерные свойства: изоляцию владельцев,
порядок реплик, постоянство меток, удаление, срок сеанса, ограничение истории,
обработку ошибок преобразования и передачу полного текущего вопроса проверяющей
модели. Модели и медиа-распознавание в них заменены тестовыми реализациями.
Это не измерение юридической правильности, качества OCR/STT или полноты обезличивания.

## Сравниваемые варианты

| Вариант | Поисковый запрос |
|---|---|
| A | Только последняя реплика |
| B | Последняя реплика + два предыдущих вопроса (`fallback_query`) |
| C | Самостоятельный запрос из `contextualize`; ошибка учитывается как fallback B |

Первый эксперимент должен использовать одну функцию `search`, одинаковый `k=8`,
один снимок корпуса, дату норм, модель векторов и параметры поиска для всех вариантов.
Нельзя сравнивать A с восемью источниками и рабочий конвейер C с объединением
нескольких выдач: различие тогда объясняется и бюджетом поиска. Рабочее объединение
исходного и преобразованного запросов (`search_issues`) оценивать отдельным вариантом
при одинаковом конечном числе источников.

## Выборка и разметка

Единица наблюдения — диалог, единица оценки — уточнение внутри него. Нужны группы:
ссылка местоимением, добавление обстоятельства, исправление прежнего обстоятельства,
смена темы, несколько проблем, ошибочный предыдущий ответ. Синтетические персональные
данные заменить метками до отправки моделей; реальные истории пользователей не нужны.

Разделять разработку и отложенную проверку **по целым диалогам и семействам сценариев**,
а не по отдельным репликам. Вопросы из существующих `labor_basic`, `labor_hard` и
`labor_compound`, использованные при настройке, могут быть только материалом разработки.
Составить отдельную новую выборку; объём и правила исключения зафиксировать до прогона.

Для каждого уточнения два участника независимо размечают набор релевантных статей
и сохраняемые/отменённые обстоятельства по тексту нормы на заданную дату.
Расхождения обсуждают до оценки моделей. В разметке указывать акт и статью, а не
только номер: одинаковые номера встречаются в разных актах.

## Метрики и воспроизводимость

- Recall@8 по всем размеченным статьям, MRR@8 первой релевантной статьи; несколько
  фрагментов одной статьи не увеличивают покрытие. Отдельно учитывать уточнения
  вне корпуса, для которых знаменатель recall не определён.
- Доля преобразований, сохранивших существенные обстоятельства, и доля добавленных
  моделью фактов; ручная проверка вслепую относительно метода, с фиксацией разногласий.
- Доля fallback с причинами и задержка преобразования/поиска по отдельности.
  Холодный старт модели отмечать отдельно; порядок методов перемешивать с записанным seed.
- Для разницы метрик — парный анализ на тех же диалогах; доверительные интервалы
  bootstrap по диалогам, чтобы не считать связанные реплики независимыми наблюдениями.

Сохранять Git commit и наличие незакоммиченных изменений, SHA-256 набора и промпта,
идентификаторы/хеши редакций корпуса, состояние индекса, модель и её digest,
параметры генерации и поиска, дату норм, seed и версии зависимостей. Для каждой
реплики сохранять преобразованный запрос, fallback, выдачу с рангами и временем.
Ошибки и пропуски включать в отчёт, а не исключать после просмотра результата.

## Границы вывода

Улучшение поиска не доказывает улучшение итогового юридического ответа. Для этого
нужен следующий отдельный эксперимент: неизменные отвечающая и проверяющая модели,
одинаковые ограничения контекста и ручная оценка ответов. Небольшой технический
smoke-прогон и вердикт второй модели не заменяют такую оценку.

Платные API-прогоны в рамках текущего этапа не запускались. Настоящий документ
не означает, что отложенная выборка уже подготовлена или эксперимент проведён.
