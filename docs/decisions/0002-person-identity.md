# Различение одноимённых участников

Дата: 16.11.2026. Статус: реализовано локально, ещё не опубликовано.

## Причина и поведение

Совпадение ФИО, в том числе в разных падежах, не устанавливает личность. Поэтому
deid больше не объединяет такие упоминания автоматически. Одно новое уникальное
имя обрабатывается как прежде. Повтор нормализованного имени внутри вопроса или
совпадение с именем из RAM-сеанса требует явного подтверждения участника.

Основной API возвращает **409** с `detail.code=person_identity_required` до
поиска норм, генерации и сохранения вопроса. Номер реплики диалога не расходуется.
В RAM-сеанс не записываются промежуточные метки и связи неразрешённого запроса.
Код отличается от конфликта/истечения сеанса, хотя HTTP-статус одинаковый.

Это консервативная политика: даже настоящий один человек, дважды названный в
разных падежах, требует подтверждения. Альтернатива — молча приписывать действия
разных людей одному участнику — не соответствует требуемому поведению.

## Ответ на неоднозначность

`detail` содержит:

- `message` — просьбу уточнить участников;
- `text_sha256` — SHA-256 точной исходной строки в UTF-8;
- `masked_text` — предварительный текст с отдельными метками обнаруженных имён;
- `groups` — группы совпадающих имён; у каждой `mentions` с исходными `start`,
  `end`, `placeholder` и `candidates` со стабильными метками текущего RAM-сеанса.

Концы диапазонов исключающие, индексы считаются в **Unicode code points** исходной
строки Python. Это не UTF-8 байты и не UTF-16 code units JavaScript. Клиенту следует
использовать предоставленные диапазоны; для подсветки в JS учитывать это различие.
Метки предварительного просмотра не являются новыми сохранёнными участниками.

## Повторный запрос

В исходный JSON `POST /api/v1/assistant/questions` добавить `person_resolution`:

```python
# detail — тело detail из ответа 409; original_payload содержит прежний text/dialog_id/date.
mentions = detail["groups"][0]["mentions"]
resolution = {
    "text_sha256": detail["text_sha256"],
    "bindings": [
        {"start": mentions[0]["start"], "end": mentions[0]["end"], "participant": "worker-a"},
        {"start": mentions[1]["start"], "end": mentions[1]["end"], "participant": "worker-b"},
    ],
}
payload = {**original_payload, "person_resolution": resolution}
```

Два одинаковых `participant` подтверждают одного участника; разные — разных.
Для одной из уже существующих меток `candidates` можно указать, например,
`participant: "[ФИО_2]"`. Такая метка должна реально существовать в текущем сеансе,
а не только в предварительном просмотре. Новый участник получает короткий
неперсональный идентификатор из ASCII букв/цифр/`_`/`-`, до 64 символов.
В диалоге эти идентификаторы можно повторно использовать для явной привязки
следующих упоминаний. Вне диалога связи действуют только в пределах запроса.

Нужно подтвердить все неразрешённые упоминания выбранной группы; частичная
привязка сохраняет 409. Изменившийся текст, неверные, пересекающиеся диапазоны,
недоступные метки и некорректная схема возвращают **422** с
`detail.code=invalid_person_resolution`. Ошибки не отражают входные ФИО.
Пользовательское подтверждение определяет связь, но не доказывает юридические факты.

Привязка может также явно указать пропущенное детектором имя. Она не должна
пересекать другую найденную сущность или частично обрезать распознанное ФИО;
диапазон должен содержать текст имени, а не телефон, метку или правовую ссылку.

## Голос и фото

Те же endpoints голосового вопроса и фото принимают multipart-поле
`person_resolution` как JSON-строку. Для голоса хеш/диапазоны относятся к полной
распознанной строке. Для фото — к результату `with_document(question, document)`,
включая служебный заголовок и используемую часть текста документа.

Распознавание при повторе выполняется заново. Если оно изменило строку, прежний
хеш отклоняется с 422. Нужно снова запросить уточнение без прежних привязок;
старые диапазоны не переносятся молча на новый результат. Отдельное хранение
исходного медиа или ожидающего подтверждения документа не добавлялось.

## Хранение и границы

`PersonMapping` содержит таблицу подстановок, подтверждённые идентификаторы
участников и псевдонимы. Всё хранится только в RAM deid, копируется транзакционно,
учитывается в лимитах памяти, очищается при удалении/истечении сеанса. TTL прежний.
Основной API не сохраняет `person_resolution`, хеш исходного текста, actor IDs
или исходные имена в вопросах, истории и trace. При ошибке связи откатываются.

Защита работает с обнаруженными или явно указанными упоминаниями. Она не является
гарантией полной детекции всех имён, автоматического разрешения местоимений,
неподтверждённых сокращений и псевдонимов. Ранее неверно объединённая история
не восстанавливается из отсутствующих исходников; для неё нужен новый диалог.
Клиентский интерфейс подсветки/выбора участников в этом backend-патче не создавался.
