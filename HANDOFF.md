## Как теперь обрабатываются одинаковые ФИО

- Одно новое уникальное обнаруженное имя обрабатывается как прежде.
- Повтор нормализованного PERSON внутри запроса или совпадение с именем RAM-сеанса
  **не объединяется автоматически**. API возвращает `409` с
  `detail.code=person_identity_required` до поиска норм и генерации.
- `detail` содержит предварительный обезличенный текст, группы упоминаний,
  исходные диапазоны и `text_sha256`. Неопределённый вопрос не сохраняется,
  номер реплики не расходуется, промежуточные RAM-изменения откатываются.
- Повторный запрос с `person_resolution` явно связывает диапазоны с одним
  участником или разными. Можно ссылаться на реально существующую метку текущего
  сеанса либо на короткий неперсональный actor ID. Одинаковые IDs подтверждают
  одного участника, разные — разных.
- SHA-256 привязывает решение к точной исходной строке. Неверные/устаревшие
  привязки возвращают безопасный `422 invalid_person_resolution`.
- Подтверждённые связи и псевдонимы хранятся только в RAM deid, охвачены
  транзакционным копированием, rollback, TTL, удалением и лимитами. В постоянную
  историю и trace не записываются исходные имена, actor IDs и решения привязки.

Полный контракт, формат JSON, мультимедиа и пример повторного запроса:
[0002-person-identity.md](docs/decisions/0002-person-identity.md).

### Особенности для клиента

409 уточнения нужно отличать от истечения/занятости сеанса по `detail.code`.
Клиент должен дать пользователю подтвердить группы и повторить **исходный**
запрос с привязками. Предварительные метки из 409 ещё не сохранены в сеансе;
их нельзя выдавать за существующие IDs участников.

Диапазоны — Unicode code points Python, не UTF-16 offsets JavaScript.
При повторе голоса/фото распознавание выполняется заново; изменившийся текст
отклоняет прежние привязки. Для фото координаты относятся ко всей строке
`with_document(question, document)`, включая заголовок. Подробности в контракте.

Политика намеренно консервативна: также просит подтверждение, когда один реальный
человек упомянут несколько раз или в разных падежах. Не возвращать прежнее
молчаливое объединение ради уменьшения числа уточнений.

## Проверки и научные ограничения

Последняя полная проверка кода перед передачей:

- **407 passed за 72.36 с** на отдельной новой БД
  `yourist_identity_20261116_test`;
- Ruff check и format — успешно, 183 Python-файла;
- новые API-тесты проверяют 409 до поиска/генерации/записи вопроса, повторное
  подтверждение same/different, безопасную историю, HTTP и мультимедиа;
- старые результаты экспериментов сохранены, реальные модели/внешние API
  для этой работы не запускались.

Фикстура `backend/tests/conftest.py` пересоздаёт схемы тестовой БД. При новом
полном прогоне сначала проверить, что `TEST_DATABASE_URL` указывает на отдельную
тестовую БД. На исходной Windows-машине команды из `backend`:

```powershell
$env:TEST_DATABASE_URL = 'postgresql+asyncpg://yourist:yourist@127.0.0.1:5432/yourist_handoff_test'
.\.venv\Scripts\python.exe -X utf8 -m pytest -q
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Окружение и запуск сервисов описаны в [README](README.md). Локальную `.venv`
нужно создать на другой машине; она не передаётся в Git. Секреты `.env` не включены.

Последняя синтетическая серия:
`backend/evaluation/results/2026-11-16-identity-clarification/`.
Два случая требуют уточнения, две пары личности остаются неразрешёнными до
ответа пользователя. Для удержанных случаев identity_merges/splits = null,
они не считаются успешным автоматическим определением личности. Детекция:
TP=13, FP=3, FN=2; грамматическое восстановление 11/15, сохранность вне меток 16/16.
Это просмотренный development-набор, а не независимая оценка качества.

**Юридическая точность Yourist ещё не установлена.** Четыре случая answers-v1
не прошли независимую человеческую разметку. Нельзя задним числом объявить ответы
пилотов эталоном, заполнять оценки своими догадками или считать новый 409
доказательством юридической правильности системы.

## Что можно делать дальше

Практический следующий кандидат для Артёма — клиентская обработка 409 уточнения:
показать упоминания/роли, позволить связать их с одним или разными участниками,
повторить исходный запрос с `person_resolution`, обработать устаревшие привязки
422 и истечение сеанса отдельно. Это предложение; перед реализацией сверить
текущий запрос владельца и выбранный клиентский стек.

Другие открытые вопросы:

- пропуски детектора имён, местоимения и неподтверждённые псевдонимы;
- устойчивый пользовательский сценарий при изменившемся OCR/STT;
- калибровка оценки юридических ответов после получения человеческого эталона;
- embedding usage пока неизвестен; контрольная запись отчёта входит во время
  случая, что важно для сравнения со старыми пилотами.

Реранкер в исследовательских B0–B3 выключен. Экспериментальные навигация C и
грамматическая коррекция D не подключались к продукту в этой работе. Полная
дорожная карта: [research-plan.md](docs/research-plan.md).
