# Независимая разметка answers-v1

Здесь находятся два исходных пакета для **разных людей** и JSON Schema поля
`label`. Четыре случая относятся к development-набору; их нельзя впоследствии
объявить независимым test. Готового эталона в этих файлах нет.

## Организатору

1. Передайте первому разметчику только `reviewer-a.json`, второму — только
   `reviewer-b.json`. Каждому приложите этот файл и `schema.json`.
2. До сдачи не передавайте ответы моделей, предполагаемые статьи, оценки другого
   разметчика и содержимое каталогов результатов. Исходный материал консультации
   указан в пакете; разметчик проверяет его, а не принимает за готовый эталон.
3. Запишите компетенции участников и порядок независимой работы. Проверка JSON
   не удостоверяет квалификацию или независимость людей.
4. Сохраните исходные сданные пакеты неизменно, отдельно от шаблонов. Импортируйте
   их в новый файл, затем разрешите расхождения с записью оснований решения.
   Пока разрешение не завершено, совпадение двух классов само по себе не даёт gold.

## Разметчику

Заполните `reviewer` своим устойчивым идентификатором, `qualification` — описанием
компетенций. Не изменяйте `dataset_sha256`, `case_id`, дату `legal_as_of`, вопрос,
факты, подвопросы и сведения об источнике. Если постановка содержит ошибку,
сообщите организатору отдельно: исправление требует новой версии набора.

Для каждого случая заполните `completed_on` (дата `YYYY-MM-DD`), `independent`
(подтверждение фактической независимости) и `label` по `schema.json`:

- `answerability`: достаточно ли фактов и источников, входит ли вопрос в область
  исследования, есть ли спорность; используйте допустимое значение из схемы;
- `issues`: решение по каждому указанному утверждению, условия, исключения,
  объяснение и нормативное основание; сохраните идентификаторы подвопросов;
- `missing_facts` и `missing_authorities`: каких фактов и источников не хватает.

Для нормы укажите акт, статью и нужную структурную единицу, редакцию на дату
случая, цитату, SHA-256 полного текста статьи и URL источника. Сверьте применимость
и текст независимо. В `evidence_alternatives` каждый внутренний список — совместно
необходимые нормы (AND), внешние списки — допустимые альтернативы (OR).

Если нормативное основание недоступно, схема допускает явную фиксацию этого:
`evidence_status: "unavailable"`, `decision: "undetermined"`, пустой
`evidence_alternatives` и содержательное `evidence_unavailable_reason`.
Не заполняйте отсутствие данных предположением. Хеш статьи подтверждает
неизменность текста; он не доказывает его актуальность или применимость.

## Импорт и следующий прогон

Из `backend` проверьте исходный набор, затем импортируйте сданные пакеты
(замените пути к `a.json` и `b.json` на реальные):

```powershell
.\.venv\Scripts\python.exe -m app.evaluation.answer_dataset evaluation/answers_v1.json
.\.venv\Scripts\python.exe -m app.evaluation.answer_dataset evaluation/answers_v1.json --reviews a.json b.json --out independently-reviewed.json
```

После разрешения расхождений импорт выполняется повторно от исходного набора
с обоими пакетами и `--adjudications`. Формат решения и правила замораживания —
в [протоколе](../../../../docs/experiments/answers-protocol.md).
Зафиксируйте принятый эталон **до нового прогона**: сохранённые ответы пилота
нельзя задним числом формально оценить как ответы на заранее принятый эталон.
После этого нужны калибровка оценщиков и новая серия сравнения качества.
