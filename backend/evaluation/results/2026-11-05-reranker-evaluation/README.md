# Локальный реранкер на фиксированных кандидатах

05.11.2026, реализация `6d461a6`; [вариант опыта](../../../../docs/experiments/reranker-protocol.md)
зафиксирован до просмотра evaluation в `85f10c4`.

Вход — history-выдача [первого этапа](../2026-11-05-dialog-evaluation/README.md).
Запросы, тексты и наборы из 24 кандидатов не меняются. Сравниваются первые 8
в исходном порядке и после cross-encoder. Нового поиска, генерации ответа или
дообучения нет. Это изолированная оценка перестановки, не всего рабочего конвейера.

Модель `BAAI/bge-reranker-v2-m3`, ревизия
`953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`. CPU float32, batch 4, 512 токенов пары,
4 потока. SHA-256 каждого файла проверен перед запуском; manifest, версии библиотек,
оценки каждого кандидата и новый порядок сохранены в [results.json](results.json).

| Метод | Recall@8 | MRR@8 |
|---|---:|---:|
| History + исходный порядок | 1,0000 | 0,9028 |
| History + реранкер | 1,0000 | 1,0000 |

Улучшились два случая: копии документов (первая релевантная статья с позиции 2 на 1)
и перевод без согласия (с позиции 3 на 1). В остальных десяти MRR не изменился.
Разница MRR +0,0972, парный 95% bootstrap-интервал **[0; 0,2361]** включает ноль.
При таком размере выборки нельзя заявлять об устойчивом превосходстве на популяции.

Development: шесть случаев, recall/MRR = 1,0 до и после; [данные](../2026-11-05-reranker-development/results.json).
После development параметры не подбирались. Evaluation выполнен один раз.

## Время и эксплуатационное решение

Загрузка модели — 4739 мс; медиана обработки 24 пар — **13995 мс**. В это время
выполнялись и другие задачи на машине, поэтому это наблюдение, не стандартизованный
бенчмарк. В отдельной проверке в Docker поиск с загрузкой/реранжированием занял
20932 мс на этапе rerank, health вернул 200, в выдаче были 8 фрагментов с score,
дата соблюдена, целевая статья найдена; fallback не сработал. Проверка использовала
копию конфигурации, постоянный `rerank=false` не менялся.

Механизм оставлен **выключенным по умолчанию**: полученный выигрыш касается порядка
в двух случаях и требует значительной дополнительной задержки. Включается через
административный API, при сбое/занятости/таймауте возвращает исходную выдачу.
Рабочие диалоги и составные вопросы переставляют объединённую выдачу до 12 источников,
а не этот пул 24 → 8; численный результат не переносится на них автоматически.

## Научные ограничения

Разметка synthetic_unreviewed, 12 сценариев, один прогон; независимой проверки
двумя людьми нет. Две целевые статьи встречались в прежнем labor_compound,
что раскрыто в отчёте первого этапа. Оценивается наличие статьи, а не нужной
части/условия статьи, юридическая правильность ответа или полнота обезличивания.
Ошибки предыдущего ответа и смена темы представлены лишь единичными примерами.

Байтовые SHA исходных JSON включают Windows CRLF; Git нормализует их в LF.
Для сравнения содержимого после checkout записаны отдельные канонические хеши
с датой последующего аудита: [input-integrity.json](input-integrity.json).
Численные результаты и исходные JSON прогонов не переписывались. В следующих
запусках стенд сразу сохраняет LF и канонический SHA входного JSON.

Повторить из backend с новым выходным каталогом:

```powershell
python -m app.evaluation.rerank_eval --input evaluation/results/2026-11-05-dialog-evaluation/results.json --model-path ../models/bge-reranker-v2-m3 --out evaluation/results/reranker-repeat
```

Описание модели: [BAAI model card](https://huggingface.co/BAAI/bge-reranker-v2-m3).
Платные API и GPU-аренда не использовались.
